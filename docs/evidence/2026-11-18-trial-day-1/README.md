**What it proves:**

- **The website's SharePoint app reads its own lists and nothing else.** Inside the site, SharePoint doesn't refuse an ungranted list with 403: it answers 200 with every item filtered out. Site Pages (the Home page) and Documents (the test file) both came back empty to the app. Outside the site, the root site and the directory are refused outright.
- **Staff roles are managed by group membership.** `setup-staff-app.ps1 -ByGroup` assigned the four groups to the four app roles, then removed the 20 personal assignments, each only after its group assignment existed (log `setup-staff-app-20261118-142022.csv`, git-ignored). A group change took effect at Ethan's next sign-in.
- **SharePoint access is least privilege by group:** baristas can't read the Schedule, and only managers and owners can change what the website publishes.

**Found and fixed on the day** (website PR with this evidence):

1. `setup-sync-app.ps1` granted list access with the older `grantedToIdentities` body, which Graph refused: 400 "'grantedTo' must be provided". Microsoft's current page for list permissions (v1.0, updated 2026-08-05, checked 2026-11-18) uses `grantedToV2`. Nothing had been granted when it failed.
2. The User Information List is hidden, so Graph's list of lists leaves it out and the grant was skipped. The script now asks for it by title.
3. `check-sync-access.mjs` expected 403 for the site's own documents and reported a FAIL on a 200. It now passes on 4xx or on an empty result, against lists known to hold items, and prints item counts only.
4. `setup-sharepoint.ps1 -WhatIf` printed no column names (a display fault only).
